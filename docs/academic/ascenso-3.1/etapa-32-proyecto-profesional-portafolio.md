# Etapa 32 — Proyecto profesional, portafolio y preparación laboral

**Prioridad:** P1 · Obligatoria  
**Estado de trabajo:** BASE DE TRABAJO ACTIVA  
**Objetivo oficial:** consolidar los conocimientos en proyectos demostrables y prepararte para trabajar profesionalmente.  
**Proyecto final:** construir una aplicación integral que reúna frontend, backend, bases de datos, infraestructura, arquitectura, pruebas automatizadas y seguridad. La aplicación tendrá documentación técnica y un informe de seguridad independiente.

## Resultados de aprendizaje
Presentar evidencia verificable de competencias; publicar repositorios profesionales; integrar proyectos Full Stack, infraestructura y seguridad; colaborar mediante revisión de código y métodos de trabajo; y preparar entrevistas y comunicación profesional.

## 32.1 — Portafolio de desarrollo
Un GitHub Profile debe mostrar proyectos relevantes, README claros, historial comprensible y contribuciones legítimas. Cada repositorio debe explicar propósito, estado, requisitos, instalación, configuración, ejecución, pruebas, arquitectura, API, capturas, demo, despliegue y limitaciones.

Incluye documentación técnica y de arquitectura suficiente para que otra persona reproduzca el proyecto. Las capturas deben evitar secretos, datos personales y pantallas que aparenten funciones no implementadas. Una demo debe estar disponible y ser segura; si no existe, declara esa limitación.

**Ejercicio:** audita tres repositorios propios con checklist de README, licencia, seguridad, tests, releases y reproducibilidad.

## 32.2 — Proyectos Full Stack
El roadmap propone sistemas de autenticación, inventario, ventas, e-commerce, dashboard administrativo, reservas, gestión empresarial y aplicaciones con comunicación en tiempo real. No es necesario construir todos por separado: selecciona un conjunto que demuestre competencias diversas y evita repetir proyectos superficiales.

Cada proyecto debe tener problema, usuarios, requisitos, modelo de datos, API, frontend, pruebas, seguridad, despliegue y documentación. Distingue simulación de operación real; por ejemplo, un flujo de pago de demostración no debe presentarse como pasarela productiva.

## 32.3 — Proyectos de infraestructura
Evidencia capacidades mediante servidor Linux, API desplegada, aplicación dockerizada, Nginx reverse proxy, pipeline CI/CD, monitorización y gestión de logs. Documenta topología, secretos, backups, actualizaciones, rollback, costos y responsabilidades. No publiques credenciales ni endpoints administrativos abiertos.

## 32.4 — Proyectos de seguridad
El portafolio puede incluir auditoría de una aplicación propia, laboratorio de reconocimiento, evaluación de vulnerabilidades, pentest documentado y autorizado, SOC de laboratorio, reglas Sigma, threat hunting, análisis de incidentes, automatización y cloud security assessment.

Cada evidencia debe indicar alcance, autorización, metodología, entorno, hallazgo, impacto, corrección y retest. No publiques datos de terceros, credenciales, información explotable de sistemas reales ni muestras peligrosas. Anonimiza y solicita permiso antes de divulgar informes.

## 32.5 — Trabajo colaborativo
Code Review debe evaluar claridad, corrección, seguridad, pruebas y mantenibilidad con comentarios respetuosos y accionables. Pull Requests describen problema, alcance, decisiones, pruebas y riesgos. Git Flow es una estrategia posible, no una obligación universal; elige branching según tamaño y cadencia del equipo.

Scrum y Kanban ayudan a coordinar trabajo; trabajo en equipo requiere comunicación técnica, gestión de tareas y resolución de conflictos. Registra decisiones y acuerdos. No utilices cantidad de commits o líneas como medida de productividad individual.

**Ejercicio:** realiza una revisión cruzada de un PR ficticio o propio; registra dos observaciones técnicas, una de seguridad y una mejora de documentación.

## 32.6 — Preparación laboral
Prepara hoja de vida, LinkedIn y portafolio web con información veraz. Practica entrevistas técnicas, conductuales, algoritmos, SQL, diseño de sistemas y presentación de proyectos. Explica decisiones, alternativas, errores y aprendizaje. La comunicación en inglés técnico forma parte del desarrollo permanente; prioriza lectura de documentación, escritura técnica y conversación progresiva.

No afirmes experiencia, certificaciones o dominio que no puedas demostrar. Prepara ejemplos STAR para experiencias reales y protege información confidencial de antiguos proyectos.

## Proyecto final — Aplicación integral
Construye una aplicación que integre:
1. Frontend accesible y responsive.
2. Backend con API documentada.
3. Base de datos y migraciones.
4. Arquitectura justificada y ADRs.
5. Autenticación y autorización por recurso.
6. Pruebas unitarias, integración y end-to-end.
7. CI/CD reproducible.
8. Despliegue documentado en entorno autorizado.
9. Docker y reverse proxy cuando correspondan.
10. Logs y monitorización básica.
11. Threat model y controles de seguridad.
12. Informe de seguridad independiente.
13. Backup, restauración y rollback.
14. README, manual de instalación y guía de usuario.
15. Demo y presentación técnica con limitaciones.

### Entregables finales
- Repositorio principal y perfil/portafolio actualizado.
- Código fuente, licencia y documentación.
- Diagramas de arquitectura y datos.
- OpenAPI y contratos.
- Evidencia de pruebas y pipeline.
- Guía de despliegue y operación.
- Informe de seguridad independiente con alcance.
- Video/demo o presentación reproducible.
- Hoja de vida y presentación de proyectos.
- Registro de limitaciones y próximos pasos.
