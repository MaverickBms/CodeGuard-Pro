# Etapa 32 — Proyecto profesional, portafolio y preparación laboral

**Prioridad:** P1 · Obligatoria  
**Estado de trabajo:** BASE DE TRABAJO ACTIVA  
**Objetivo oficial:** consolidar los conocimientos en proyectos demostrables y prepararte para trabajar profesionalmente.  
**Proyecto final:** construir una aplicación integral que reúna frontend, backend, bases de datos, infraestructura, arquitectura, pruebas automatizadas y seguridad. La aplicación tendrá documentación técnica y un informe de seguridad independiente.

## Resultados de aprendizaje
Presentar evidencia verificable de competencias; publicar repositorios profesionales; integrar proyectos Full Stack, infraestructura y seguridad; colaborar mediante revisión de código y métodos de trabajo; y preparar entrevistas y comunicación profesional.

## 32.1 — Portafolio de desarrollo
Un GitHub Profile debe mostrar proyectos relevantes, README claros, historial comprensible y contribuciones legítimas. Cada repositorio debe explicar propósito, estado, requisitos, instalación, configuración, ejecución, pruebas, arquitectura, API, capturas, demo, despliegue y limitaciones.

Incluye documentación técnica y de arquitectura suficiente para que otra persona reproduzca el proyecto. Las capturas deben evitar secretos, datos personales y pantallas que aparenten funciones no implementadas. Una demo debe estar disponible y ser segura; si no existe, declara esa limitación.

**Ejercicio:** audita tres repositorios propios con checklist de README, licencia, seguridad, tests, releases y reproducibilidad.

## 32.2 — Proyectos Full Stack
El roadmap propone sistemas de autenticación, inventario, ventas, e-commerce, dashboard administrativo, reservas, gestión empresarial y aplicaciones con comunicación en tiempo real. No es necesario construir todos por separado: selecciona un conjunto que demuestre competencias diversas y evita repetir proyectos superficiales.

Cada proyecto debe tener problema, usuarios, requisitos, modelo de datos, API, frontend, pruebas, seguridad, despliegue y documentación. Distingue simulación de operación real; por ejemplo, un flujo de pago de demostración no debe presentarse como pasarela productiva.

## 32.3 — Proyectos de infraestructura
Evidencia capacidades mediante servidor Linux, API desplegada, aplicación dockerizada, Nginx reverse proxy, pipeline CI/CD, monitorización y gestión de logs. Documenta topología, secretos, backups, actualizaciones, rollback, costos y responsabilidades. No publiques credenciales ni endpoints administrativos abiertos.

## 32.4 — Proyectos de seguridad
El portafolio puede incluir auditoría de una aplicación propia, laboratorio de reconocimiento, evaluación de vulnerabilidades, pentest documentado y autorizado, SOC de laboratorio, reglas Sigma, threat hunting, análisis de incidentes, automatización y cloud security assessment.

Cada evidencia debe indicar alcance, autorización, metodología, entorno, hallazgo, impacto, corrección y retest. No publiques datos de terceros, credenciales, información explotable de sistemas reales ni muestras peligrosas. Anonimiza y solicita permiso antes de divulgar informes.

## 32.5 — Trabajo colaborativo
Code Review debe evaluar claridad, corrección, seguridad, pruebas y mantenibilidad con comentarios respetuosos y accionables. Pull Requests describen problema, alcance, decisiones, pruebas y riesgos. Git Flow es una estrategia posible, no una obligación universal; elige branching según tamaño y cadencia del equipo.

Scrum y Kanban ayudan a coordinar trabajo; trabajo en equipo requiere comunicación técnica, gestión de tareas y resolución de conflictos. Registra decisiones y acuerdos. No utilices cantidad de commits o líneas como medida de productividad individual.

**Ejercicio:** realiza una revisión cruzada de un PR ficticio o propio; registra dos observaciones técnicas, una de seguridad y una mejora de documentación.

## 32.6 — Preparación laboral
Prepara hoja de vida, LinkedIn y portafolio web con información veraz. Practica entrevistas técnicas, conductuales, algoritmos, SQL, diseño de sistemas y presentación de proyectos. Explica decisiones, alternativas, errores y aprendizaje. La comunicación en inglés técnico forma parte del desarrollo permanente; prioriza lectura de documentación, escritura técnica y conversación progresiva.

No afirmes experiencia, certificaciones o dominio que no puedas demostrar. Prepara ejemplos STAR para experiencias reales y protege información confidencial de antiguos proyectos.

## Proyecto final — Aplicación integral
Construye una aplicación que integre:
1. Frontend accesible y responsive.
2. Backend con API documentada.
3. Base de datos y migraciones.
4. Arquitectura justificada y ADRs.
5. Autenticación y autorización por recurso.
6. Pruebas unitarias, integración y end-to-end.
7. CI/CD reproducible.
8. Despliegue documentado en entorno autorizado.
9. Docker y reverse proxy cuando correspondan.
10. Logs y monitorización básica.
11. Threat model y controles de seguridad.
12. Informe de seguridad independiente.
13. Backup, restauración y rollback.
14. README, manual de instalación y guía de usuario.
15. Demo y presentación técnica con limitaciones.

- Evidencia de pruebas y pipeline.

- Informe de seguridad independiente con alcance.
- Video/demo o presentación reproducible.

- Registro de limitaciones y próximos pasos.

## Desglose granular de lecciones oficiales — etapa 32

Este desglose conserva los títulos y el orden del roadmap maestro. Las orientaciones organizan el estudio y la aplicación en proyectos controlados; no equivalen a validación de proveedores, certificación, ejecución de laboratorios ni experiencia laboral demostrada.

### Módulo 32.1 — Portafolio de desarrollo

#### 32.1.01 — GitHub Profile
GitHub Profile presenta identidad técnica, proyectos y contribuciones públicas. Mantén descripción veraz, enlaces activos y actividad representativa; no publiques correo privado, tokens ni datos personales innecesarios.


**Práctica y evidencia:** Revisa perfil GitHub con bio técnica, enlaces y proyectos fijados. **Evidencia:** presenta perfil coherente sin publicar datos personales innecesarios.

#### 32.1.02 — Repositories
Repositories organizan código, historial, issues y configuración de proyectos. Mantén nombres claros, licencia adecuada, estructura reproducible y reglas de contribución.


**Práctica y evidencia:** Organiza repositorios por proyecto con nombres, licencias y estado claros. **Evidencia:** un visitante identifica propósito y mantenimiento de cada repositorio.

#### 32.1.03 — README
README explica propósito, funcionalidades, requisitos, instalación, configuración, ejecución y limitaciones del proyecto. Prueba cada instrucción desde un entorno limpio y no incluyas secretos.


**Práctica y evidencia:** Escribe README con problema, funciones, stack, instalación, uso, pruebas y capturas. **Evidencia:** otra persona reproduce el proyecto siguiendo el documento.

#### 32.1.04 — Technical Documentation
Technical Documentation explica arquitectura, módulos, contratos, dependencias y operación. Usa diagramas y ejemplos actualizados y documenta decisiones y límites conocidos.


**Práctica y evidencia:** Documenta decisiones, configuración, dependencias y operación del proyecto. **Evidencia:** un desarrollador nuevo puede ejecutar y mantenerlo.

#### 32.1.05 — Architecture Documentation
Architecture Documentation describe componentes, relaciones, límites de confianza y decisiones arquitectónicas. Mantén vistas dirigidas a audiencias concretas y sincronizadas con la implementación real.


**Práctica y evidencia:** Dibuja arquitectura con componentes, dependencias, límites de confianza y despliegue. **Evidencia:** cada diagrama tiene audiencia y alcance.

#### 32.1.06 — API Documentation
API Documentation describe endpoints, métodos, esquemas, autenticación, errores y ejemplos reproducibles. Usa OpenAPI cuando proceda y verifica que coincide con la versión desplegada.


**Práctica y evidencia:** Publica especificación API con endpoints, esquemas, autenticación y errores. **Evidencia:** consumidor reproduce una llamada sin consultar código.

#### 32.1.07 — Screenshots
Screenshots muestran interfaz y flujos del proyecto como evidencia visual. Usa datos ficticios, elimina información sensible y etiqueta versión/entorno para evitar confundir prototipo con producción.


**Práctica y evidencia:** Captura pantallas sin datos reales, tokens ni información privada. **Evidencia:** cada imagen demuestra una función específica.

#### 32.1.08 — Demo
Demo permite observar una funcionalidad mediante entorno accesible, video o sesión guiada. Explica precondiciones y limitaciones y no presentes mocks o datos simulados como operaciones reales.


**Práctica y evidencia:** Graba demo corta con flujo de usuario, limitaciones y entorno. **Evidencia:** la demo corresponde a una versión reproducible.

#### 32.1.09 — Deployment
Deployment publica el proyecto en un entorno controlado y accesible. Documenta proveedor, configuración, variables, TLS, observabilidad, backups y rollback; nunca expongas secretos en el repositorio.


**Práctica y evidencia:** Despliega proyecto en entorno autorizado con configuración segura y health check. **Evidencia:** documenta URL, versión y procedimiento de rollback sin publicar secretos.

#### 32.1.10 — Project Presentation
Project Presentation comunica problema, usuarios, arquitectura, decisiones, contribución y resultados. Adapta el nivel técnico a la audiencia y distingue capacidades terminadas, prototipos y trabajo pendiente.


**Práctica y evidencia:** Prepara presentación que explique problema, decisiones, arquitectura, trade-offs y resultados. **Evidencia:** responde preguntas técnicas con pruebas.

### Módulo 32.2 — Proyectos Full Stack

#### 32.2.01 — Sistema de autenticación
Un sistema de autenticación debe gestionar registro, inicio, sesión, recuperación, MFA y cierre de forma segura. Implementa protocolos y bibliotecas mantenidas, almacena contraseñas con hashing adaptativo y prueba revocación.


**Práctica y evidencia:** Define alcance, amenazas y pruebas para un sistema de autenticación. **Evidencia:** demuestra hash seguro, recuperación, sesiones y autorización.

#### 32.2.02 — Sistema de inventario
Un sistema de inventario administra productos, existencias, movimientos y trazabilidad. Define invariantes de stock, concurrencia, auditoría y permisos antes de implementar operaciones CRUD.


**Práctica y evidencia:** Modela inventario con productos, movimientos y auditoría. **Evidencia:** demuestra consistencia de stock con pruebas de concurrencia.

#### 32.2.03 — Sistema de ventas
Un sistema de ventas registra pedidos, líneas, pagos y estados del proceso. Modela transacciones, idempotencia, impuestos y conciliación según requisitos y no almacenes datos de pago sensibles sin controles aplicables.


**Práctica y evidencia:** Construye flujo de ventas con clientes, detalle, pagos e inventario. **Evidencia:** prueba transacción, errores y reversión.

#### 32.2.04 — E-commerce
E-commerce integra catálogo, carrito, pedidos, pagos y logística. Protege sesiones, precios y autorización en servidor, valida callbacks de pago y evita confiar en importes enviados por el cliente.


**Práctica y evidencia:** Desarrolla e-commerce de demostración con catálogo, carrito y pedido. **Evidencia:** verifica validación, autorización y datos de prueba.

#### 32.2.05 — Dashboard administrativo
Un dashboard administrativo presenta indicadores y acciones para gestionar una operación. Define roles, filtros, actualización de datos y estados vacíos/error y evita mostrar información fuera del permiso del usuario.


**Práctica y evidencia:** Implementa dashboard con métricas definidas y consultas trazables. **Evidencia:** explica origen y actualización de cada indicador.

#### 32.2.06 — Sistema de reservas
Un sistema de reservas gestiona disponibilidad, horarios, confirmaciones y cancelaciones. Controla concurrencia para evitar doble reserva, define zonas horarias y registra cambios de estado.


**Práctica y evidencia:** Modela reservas con disponibilidad, zona horaria y prevención de doble reserva. **Evidencia:** prueba concurrencia y cancelación.

#### 32.2.07 — Sistema de gestión empresarial
Un sistema de gestión empresarial integra procesos y datos de varias áreas. Define límites de dominio, auditoría, permisos y migración de datos; evita construir un monolito sin módulos ni reglas claras.


**Práctica y evidencia:** Define módulos y límites de un sistema de gestión empresarial. **Evidencia:** demuestra separación de responsabilidades y permisos.

#### 32.2.08 — Aplicación con comunicación en tiempo real
Una aplicación en tiempo real intercambia eventos o mensajes con baja latencia mediante WebSockets o tecnologías equivalentes. Define reconexión, autorización por canal, orden y límites de mensajes.


**Práctica y evidencia:** Implementa comunicación en tiempo real con autenticación y control de canales. **Evidencia:** prueba reconexión, autorización y límites.

### Módulo 32.3 — Proyectos de infraestructura

#### 32.3.01 — Servidor Linux
Un servidor Linux desplegado debe tener sistema soportado, usuarios mínimos, SSH seguro, firewall, parches y monitoreo. Documenta configuración y procedimiento de recuperación.


**Práctica y evidencia:** Despliega un servidor Linux de prueba con SSH, usuarios y firewall endurecidos. **Evidencia:** registra baseline y procedimiento de recuperación.

#### 32.3.02 — API desplegada
Una API desplegada debe ofrecer contrato estable, TLS, autenticación, autorización, límites y observabilidad. Prueba salud, errores, paginación y recuperación antes de declararla disponible.


**Práctica y evidencia:** Publica API de laboratorio detrás de HTTPS y health check. **Evidencia:** prueba autenticación, logs y disponibilidad.

#### 32.3.03 — Aplicación Dockerizada
Una aplicación Dockerizada empaqueta runtime y dependencias en una imagen reproducible. Usa imágenes base mantenidas, usuario no root, escaneo y configuración externa sin secretos en capas.


**Práctica y evidencia:** Construye imagen Docker no root y escaneada. **Evidencia:** fija digest, registra CVEs y documenta runtime.

#### 32.3.04 — Nginx Reverse Proxy
Nginx Reverse Proxy enruta solicitudes a servicios internos y puede terminar TLS y aplicar límites. Configura hosts, headers, timeouts y logs y verifica que no exponga endpoints internos.


**Práctica y evidencia:** Configura Nginx como reverse proxy con TLS y cabeceras apropiadas. **Evidencia:** verifica upstream, redirección y logs.

#### 32.3.05 — Pipeline CI/CD
Un pipeline CI/CD compila, prueba, analiza y despliega artefactos con trazabilidad. Protege runners y secretos, exige aprobaciones adecuadas y conserva evidencia de cada versión.


**Práctica y evidencia:** Crea pipeline CI/CD con lint, tests, build y despliegue a staging. **Evidencia:** demuestra gate fallido y rollback.

#### 32.3.06 — Monitorización
Monitoring recoge métricas y señales para observar salud y rendimiento del sistema. Define SLOs, alertas accionables, dashboards y responsables de respuesta.


**Práctica y evidencia:** Configura métricas y alertas para latencia, errores y disponibilidad. **Evidencia:** presenta dashboard y runbook.

#### 32.3.07 — Gestión de logs
Gestión de logs centraliza eventos para diagnóstico, auditoría y seguridad. Establece formato, retención, sincronización y control de acceso y redacta credenciales y datos personales.


**Práctica y evidencia:** Centraliza logs con retención, correlación y redacción de secretos. **Evidencia:** reconstruye una solicitud mediante trace/correlation ID.

### Módulo 32.4 — Proyectos de seguridad

#### 32.4.01 — Auditoría de una aplicación propia
Una auditoría de aplicación propia evalúa alcance, arquitectura, controles, dependencias y vulnerabilidades con permiso explícito. Documenta metodología, evidencia, limitaciones y remediación.


**Práctica y evidencia:** Audita una aplicación propia con autorización y alcance definido. **Evidencia:** presenta hallazgos reproducibles y remediación.

#### 32.4.02 — Laboratorio de reconocimiento
Un laboratorio de reconocimiento define activos ficticios, fuentes y límites para aprender descubrimiento. Mantén red aislada, documenta autorización y evita consultar sistemas de terceros.


**Práctica y evidencia:** Ejecuta reconocimiento solo en un laboratorio aislado y registra alcance. **Evidencia:** documenta fuentes y límites.

#### 32.4.03 — Evaluación de vulnerabilidades
Una evaluación de vulnerabilidades identifica debilidades y prioriza riesgo según exposición e impacto. Valida falsos positivos y entrega plan de corrección con responsable.


**Práctica y evidencia:** Evalúa vulnerabilidades en entorno de prueba y valida falsos positivos. **Evidencia:** prioriza por riesgo y evidencia.

#### 32.4.04 — Pentesting documentado
Un pentesting documentado demuestra metodología, alcance, autorización, pruebas controladas y resultados. Limita evidencias, no incluyas datos sensibles y distingue vulnerabilidades confirmadas de hipótesis.


**Práctica y evidencia:** Documenta un pentest autorizado con metodología, hallazgos y cierre. **Evidencia:** incluye Rules of Engagement y cadena de custodia.

#### 32.4.05 — Laboratorio SOC
Un laboratorio SOC integra logs sintéticos, reglas y flujo de triage para practicar detección. Evalúa cobertura y falsos positivos y mantiene el entorno sin datos reales.


**Práctica y evidencia:** Despliega un SOC pequeño con logs sintéticos y casos de uso. **Evidencia:** demuestra alerta, triage y escalamiento.

#### 32.4.06 — Reglas Sigma
Reglas Sigma describen detecciones de forma portable entre backends compatibles. Documenta fuente de log, condición, referencias y pruebas positivas/negativas.


**Práctica y evidencia:** Escribe reglas Sigma y pruébalas con eventos sintéticos. **Evidencia:** conserva dataset y resultado esperado.

#### 32.4.07 — Threat Hunting
Threat Hunting utiliza hipótesis para buscar señales en telemetría disponible. Registra consultas, fuentes, ventana temporal, evidencia y limitaciones y evita conclusiones sin corroboración.


**Práctica y evidencia:** Realiza threat hunting basado en hipótesis y fuentes definidas. **Evidencia:** registra consultas, señales y conclusión.

#### 32.4.08 — Análisis de incidentes
Análisis de incidentes reconstruye cronología, alcance, causa e impacto con evidencia preservada. Mantén cadena de custodia y separa hechos de inferencias.


**Práctica y evidencia:** Reconstruye incidente simulado con timeline y evidencia preservada. **Evidencia:** distingue hechos e hipótesis.

#### 32.4.09 — Automatización de seguridad
Automatización de seguridad integra recolección, análisis, enriquecimiento y notificación. Usa permisos mínimos, idempotencia, logs y aprobación para acciones disruptivas.


**Práctica y evidencia:** Automatiza una tarea defensiva con aprobación humana y logs. **Evidencia:** demuestra idempotencia y control de permisos.

#### 32.4.10 — Cloud Security Assessment
Cloud Security Assessment revisa IAM, redes, almacenamiento, logging y configuración cloud dentro de cuentas autorizadas. Limita permisos, protege reportes y prioriza remediación verificable.


**Práctica y evidencia:** Evalúa configuración cloud mediante checklist y alcance autorizado. **Evidencia:** prioriza hallazgos sin crear recursos no aprobados.

### Módulo 32.5 — Trabajo colaborativo

#### 32.5.01 — Code Review
Code Review evalúa cambios en corrección, seguridad, mantenibilidad y pruebas. Revisa intención y riesgos, solicita cambios concretos y conserva un tono respetuoso.


**Práctica y evidencia:** Revisa un pull request con foco en corrección, seguridad, pruebas y mantenibilidad. **Evidencia:** deja comentarios accionables y vinculados a líneas.

#### 32.5.02 — Pull Requests
Pull Requests proponen cambios para revisión y trazabilidad antes de integrar. Incluye contexto, alcance, pruebas, capturas pertinentes y riesgos; no mezcles cambios ajenos al objetivo.


**Práctica y evidencia:** Crea PR con descripción, contexto, pruebas y capturas pertinentes. **Evidencia:** el revisor puede entender y validar el cambio.

#### 32.5.03 — Git Flow
Git Flow es un modelo de ramas con convenciones para desarrollo y releases. Comprende coste y alternativas más simples; el equipo debe adoptar un flujo explícito y consistente.


**Práctica y evidencia:** Aplica flujo Git con ramas, commits pequeños y resolución documentada de conflictos. **Evidencia:** conserva historial claro y evita commits de secretos.

#### 32.5.04 — Scrum
Scrum organiza trabajo iterativo mediante responsabilidades, eventos y artefactos. Participa en planificación, revisión y retrospectiva con objetivos y feedback verificables.


**Práctica y evidencia:** Simula Sprint con objetivo, backlog y review. **Evidencia:** documenta incremento y feedback.

#### 32.5.05 — Kanban
Kanban visualiza flujo y limita WIP para mejorar entrega. Define políticas de columnas y mide tiempo de ciclo y bloqueos.


**Práctica y evidencia:** Gestiona tablero Kanban con WIP y bloqueos. **Evidencia:** mide flujo y propone mejora.

#### 32.5.06 — Trabajo en equipo
Trabajo en equipo requiere acuerdos sobre responsabilidades, revisión, comunicación y resolución de dependencias. Comparte contexto y solicita ayuda temprano.


**Práctica y evidencia:** Define responsabilidades y acuerdos de trabajo para un equipo pequeño. **Evidencia:** documenta decisiones y entregables.

#### 32.5.07 — Comunicación técnica
Comunicación técnica transmite decisiones, riesgos y resultados con precisión y audiencia adecuada. Distingue hechos, supuestos y recomendaciones y documenta acuerdos.


**Práctica y evidencia:** Redacta un informe técnico para audiencia no especializada y una nota técnica para desarrolladores. **Evidencia:** adapta lenguaje sin perder precisión.

#### 32.5.08 — Gestión de tareas
Gestión de tareas descompone objetivos en unidades estimables, priorizadas y verificables. Define responsable, dependencias, criterios de cierre y seguimiento.


**Práctica y evidencia:** Divide una entrega en tareas estimables con dependencia y criterio de terminado. **Evidencia:** demuestra seguimiento y ajuste.

#### 32.5.09 — Resolución de conflictos
Resolución de conflictos busca comprender intereses y evidencia y acordar acciones. Separa problema técnico de diferencias personales y escala cuando afecte seguridad o integridad.


**Práctica y evidencia:** Resuelve un conflicto técnico mediante alternativas, criterios y decisión registrada. **Evidencia:** documenta trade-offs sin personalizar desacuerdo.

### Módulo 32.6 — Preparación laboral

#### 32.6.01 — Hoja de vida
La hoja de vida resume experiencia, formación, proyectos y habilidades relevantes para un rol. Usa fechas y logros verificables y no atribuyas trabajo colectivo como contribución individual.


**Práctica y evidencia:** Adapta hoja de vida a una vacante con logros medibles y tecnologías demostrables. **Evidencia:** cada afirmación se respalda con proyecto o experiencia real.

#### 32.6.02 — LinkedIn
LinkedIn presenta trayectoria y contactos profesionales en un perfil público. Mantén información consistente con la hoja de vida y evita publicar datos confidenciales de empleadores o clientes.


**Práctica y evidencia:** Completa LinkedIn con titular, experiencia, proyectos y habilidades verificables. **Evidencia:** evita certificaciones o cargos no obtenidos.

#### 32.6.03 — Portafolio web
Un portafolio web reúne proyectos, casos de estudio y enlaces verificables. Incluye propósito, rol, arquitectura, capturas, demo, limitaciones y resultados reales.


**Práctica y evidencia:** Publica portafolio web accesible, responsivo y con enlaces funcionales. **Evidencia:** verifica rendimiento y ausencia de datos sensibles.

#### 32.6.04 — Entrevistas técnicas
